# Level 1 高负载导致 GPU 卡死 —— 排查报告

日期：2026-09-27
现场：`file:///C:/Users/Administrator/Desktop/work/backrooms.html`（standalone，buildId `28d3c3eae785`）Level 1
现象：移动到某一位置后 GPU 使用率短时间内涨到 100%（涨幅 >50%），约十几秒后 RTX 3070 停止向显示器输出画面、但继续高负载，1~2 分钟后强制关机。测试前显卡已外置加强散热。

---

## 一、结论

1. **游戏里不存在"无界负载"**：没有无限循环、没有每帧新建几何/贴图、没有运行期增删光源、显存占用很小（Level 1 全部贴图 74.0 MiB）。Level 1 的负载上限是可测的、有界的。
2. **但 Level 1 是全项目最重的关卡**：网格 431、材质 147、贴图 74.0 MiB 都是 16 关第一；点光源 36 盏（仅次于 Level 4 的 37）。而且它的负载**强烈随位置与朝向变化**：最轻的视野 0.80 ms / 69 次 draw call，最重的视野 10.60 ms / **1315 次 draw call**，相差 **13.25×**——最重的区域正是地图中央大厅（列 6–26 × 行 16–31），也就是从电梯出来那一片。
3. **"显示器没画面但 GPU 仍满载 1~2 分钟"这一步发生在驱动/硬件层**，不是浏览器能制造的状态，浏览器也无法从这种状态恢复。游戏的贡献是把 GPU 长时间顶在接近 100%（尤其 4K + 高画质 + 36 盏点光源 + GTAO/阴影三遍提交场景）。散热不足时，长时间满载会把这种"顶到边缘"变成一次真正的挂死。
4. **顺手修掉一个真实缺陷**：低画质档并没有省掉 Level 1 / Level 4 的点光源（仍是 36 / 37 盏），等于"性能模式"仍然全额支付最贵的片元成本。已改为按画质分级（低画质 8 盏），低画质同一视野的帧工作量下降 35%~45%，高画质外观零变化。

## 三、负载随位置变化（真实 Level 1 + 真实 `createRenderingPipeline`，1280×720，pixelRatio 1，高画质）

采样方式：45×33 网格按 5 步长取 52 个可站立格（朝向 0）+ 5 个点各 4 个朝向，共 72 个样本；每样本渲染 3 帧预热 + 4~5 帧计时，每帧尾 `gl.finish()` 取中位数。

| 指标 | 最小 | 中位 | 最大 |
| --- | --- | --- | --- |
| 单帧工作量 | **0.80 ms** | 4.70 ms | **10.60 ms**（13.25×） |
| draw call | 69 | — | **1315** |
| 三角形 | 14,285 | — | 183,717 |

最重的样本：`(6,21)` 10.6 ms / 1007 calls、`(26,21)` 9.2 ms、`(16,26)` 8.6 ms、`(16,21)` 7.7 ms、`(21,26)` 7.4 ms —— 都在中央大厅。
最轻的样本：`(1,6)`/`(1,1)` 0.8 ms、`(36,1)` 1.4 ms、`(41,31)` 1.6 ms —— 都在地图边缘走廊。

也就是说：**从边缘走廊走进中央大厅，视野内的对象数会从 ~70 涨到 ~1300，单帧成本涨一个数量级**。这就是"移动到某个位置 GPU 突然飙升"的直接来源。

### 分辨率放大（同一批采样点）

| 渲染分辨率 | 像素数 | 最重视野单帧 |
| --- | --- | --- |
| 1280×720 | 0.92 MP | 6.0–6.8 ms |
| 2560×1250 | 3.20 MP | 6.7–8.9 ms |
| 3840×1880 | 7.22 MP | 10.4 ms |

像素数涨 7.8×，时间只涨 1.7× ⇒ **不是填充率瓶颈，而是"每帧提交量"瓶颈**（~1300 次 draw call 在 Chrome + three.js 上的固定开销），分辨率只承担其中约 40%。

对照实验：把渲染目标推到 7680×3760（4× 你的像素）时，**浏览器的 GPU 进程直接卡住** —— 标签页不再响应任何 DOM 查询，最终只能关闭标签页。说明后处理链（EffectComposer 的 HDR 目标 + GTAO 的 4~5 个半分辨率目标 + 4×MSAA）在超大像素数下存在悬崖。这次没有（也不建议）在 4K 上做同样的对照。

## 四、逐条排除的"不是原因"

| 怀疑点 | 排查结果 |
| --- | --- |
| 无限/无界循环 | 全仓库 `while` / `for(;;)` 只有二叉堆下沉、音频声部补齐、迷宫生成等有限循环；渲染路径没有循环 |
| 每帧新建几何/贴图/缓冲 | `needsUpdate` 全部出现在构建期；运行期没有新建 GPU 资源 |
| 显存不足 | 单关卡贴图 ≤ 74 MiB、几何 ≤ 16 MiB，8 GB 显存绰绰有余 |
| 运行期增删光源导致全关卡 shader 重编译 | 不会：`check-light-count-stability` 走完 16 关确认光源清单恒定；hound/smiler/firesalt/出口/电梯的灯都是构建期创建，运行期只改 intensity |
| 走进新区才上传贴图造成卡顿 | 基本被 `prewarm()` 覆盖：实测走一圈只新增 1 张贴图、4 个 program |
| 关卡切换/预加载 | 切换发生在电梯触发时，本次现象不符；且切换前只是构建下一关场景 |
| 手臂/人体模型（本会话新增） | Level 1 阴影投射者就是这 24 个网格（43,370 三角形），数量级上无关 |

## 五、最可能的事件链（推断，已标注证据强度）

1. 【已实测】Level 1 走进中央大厅时单帧提交 1000+ 次 draw call；在 4K 下这一视野约 10 ms 的单帧工作量，叠加 4K 画布合成、HUD/滤镜层、以及像素比上限 1.25（最大 11.3 MP）后，GPU 基本贴顶。
2. 【已实测】自适应画质存在 54–58 FPS 死区：`main.js:2520` 只有 `< 54` 才降档、`2522` 只有 `> 58` 才升档；`rendering-pipeline.js:338` 在 54–58 之间不做任何事。也就是说卡在 55–58 FPS 时游戏**不会做任何减负**，GPU 可以长时间维持 100%。
3. 【推断】长时间 100% 满载 + 散热不足 ⇒ 显卡在驱动/硬件层挂死：显示输出先断，GPU 仍显示满载，系统无法自行恢复。这一步不是浏览器应用能制造或恢复的状态。
4. 【对应】你刚做的外置散热正是针对第 3 步的处置；第 1、2 步的游戏侧余量见下节。

## 七、后续可选（按代价从低到高，尚未实施）

1. **去掉自适应画质的 54–58 死区**：把降档阈值改成"低于目标帧率持续一段时间就降"，并允许先降分辨率（现在分辨率是最后一道）。影响所有关卡，`main.js` + `rendering-pipeline.js` 都在被另一条工作流改动，需要协调。
